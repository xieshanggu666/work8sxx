# 🎲 营销活动抽奖与积分激励运营平台

基于 **Vue 3 + Vite + Pinia** 的营销运营平台，覆盖抽奖玩法、积分体系与运营管理。

## 功能特性

- **多玩法抽奖**
  - 🎡 幸运转盘（SVG 扇形 + 旋转动画）与 🎰 刮刮乐（Canvas 刮涂层揭晓）
  - 加权随机抽取、奖品库存扣减、积分奖品自动入账
- **抽奖任务自动结算**：任务进度按真实参与记录累计（正常 + 审核放行计入；风控冻结暂缓、撤销不计），达标自动发奖并同步积分流水；风控放行后按记录归属业务日补计、撤销后确认回退；任务进度与领奖记录按业务日归档台账，跨日审核不串账、不重复发奖
- **风控校验**：每日限抽 / 累计限抽 / 奖品库存余量 / 积分不足拦截
- **风控申诉**：抽奖与兑换命中可配置规则时生成风险审核单，冻结相关积分、预占奖品/商品库存；用户可申诉，运营审核后放行（发奖/核销）或撤销（返还积分/库存/次数）；角色权限 + 全量操作记录，状态机保证幂等防重复扣减
- **积分库存对账**：按业务日核对抽奖成本/中奖积分、兑换扣减/撤销返还、任务奖励与积分流水、风控冻结、奖品/商品库存，生成可追溯差异单（P1 积分发生额 / P2 任务台账逐笔 / P3 余额链 / P4 冻结单据 / P5 库存账实）；运营复核后仅以 append-only 补偿流水与库存调整凭证修正，保留全部原始记录；积分流水作为历史对账、余额链与奖励统计底账不裁剪，差异签名幂等防重复执行/重复补偿，任务发奖与补偿统一按领奖台账 id 勾稽，跨日审核与补偿按业务日归属、实际处理日单独留痕，余额、库存、看板即时同步
- **积分体系**：签到与任务赚积分、积分明细流水（含冻结/返还/放行/任务结算/对账补偿标记）、积分商城兑换
- **实物收货发货**：中奖或兑换的**实物奖品/商品**自动生成发货单，用户填写/修改收货信息（姓名、手机号、地区、详细地址），运营接单并录入快递公司/单号发货，用户查看物流后确认收货；状态机 `待填地址 → 待发货 → 已发货 → 已收货`，冻结/撤销的风控单不产生发货单，全部操作留痕
- **卡券账户与核销**：中奖或兑换**券类奖品/商品**（满减券/代金券/兑换券）自动发券至卡券账户，一券一全局唯一券码；风控命中时只**预占**券库存（不发券），放行后**交付**发券（有效期自放行日起算）、撤销则**释放**预占（券始终不发出）。用户在「🎟️ 卡券核销」出示/复制券码，运营扫码或输码核销，状态机拦截重复核销与到期核销；按业务动作做卡券到期扫描（到期自动失效），发放/预占/交付/核销/到期/补券全部写入 append-only 卡券台账。对账新增 **P6 卡券账户勾稽**（有效券记录发券、券码唯一、核销信息、到期状态），漏发可按差异单补发新券（新券码、有效期自补券日起算，append-only 不伪造历史），孤立券/重复码人工核查；券库存仍由 P5 统一勾稽，看板/Tab 角标同步
- **运营侧**：运营看板（累计抽奖、参与人数、中奖统计、库存、待风控/冻结积分、任务结算量、对账业务日/待复核/补偿统计、实物发货各状态单量、卡券发放/待核销/已核销/过期/预占）、活动管理（新建 / 暂停 / 重置库存 / 删除）
- **演示友好**：内置多套 mock 活动、预置用户积分、预置风控审核单（待审/已申诉/已放行/已撤销/跨日待审）、历史业务日任务台账与一笔历史漏记差异、卡券账户（待核销满减券/今日与历史已核销券/已过期券 + 一张风控预占待交付的视频月卡），纯前端零后端即可浏览运行

## 抽奖任务自动结算说明

- **进度来源**：抽奖任务（如「今日抽奖3次」）进度唯一来源于真实参与记录——状态为 `正常` 与 `已放行` 的抽奖记录计入；`冻结` 暂缓计入，`撤销` 不计入。无手动领取入口，杜绝刷任务与重复发奖。
- **自动结算**：每次有效参与落账后按归属业务日结算，达标即自动发放奖励并写入积分流水（`任务结算：xxx`）；同一（任务 × 业务日）仅发奖一次（`taskClaims` 台账判重），发奖流水记录台账 `refId`，重复触发、历史流水留存检查与对账补偿均以此统一幂等跳过。
- **风控联动**
  - 冻结：该笔暂缓计入，任务页与审核单均提示"审核中暂缓"；
  - 放行：按参与记录的**归属业务日**补计进度，若达标自动补发奖励（流水与台账标注"跨日补计"），不计入审核当日，避免跨日串账；
  - 撤销：该笔确认不计入（冻结期未计入，撤销后自然回退），积分/库存/限次按既有规则返还。
- **按业务日归档**：积分中心「任务结算记录」按业务日分册展示每日进度、审核中笔数与领奖记录（含归属日/发放日）；业务日切换时先兜底结算上一日再归档，历史台账保留不丢。
- **同步积分流水**：任务奖励实时入账并写 append-only 流水；跨日补计的流水日期为实际发放日、备注归属业务日，保证账实一致。
- 逻辑冒烟测试：`npm run test:settle`（覆盖进度累计/冻结暂缓/放行补计/撤销回退/幂等防重/跨日隔离）。

## 积分库存对账说明

- **对账口径（按业务日）**
  - **P1 积分发生额**：由业务记录逐笔推导应有净额——抽奖成本（落账即扣）、中奖积分（正常按参与日 / 放行按原参与日归属）、兑换扣减、撤销返还（按审核日）、任务奖励（含跨日补计，按归属业务日）——与积分流水实际净额勾稽，补偿流水单列；
  - **P2 任务奖励台账**：`taskClaims` 每笔领奖必须有对应流水，原始发奖流与 `task-comp` 补偿流均按台账 id 精确勾稽（旧种子无 id 时按任务名+金额+业务日兜底）；
  - **P3 余额链**：append-only 流水的余额快照按时间重放必须逐笔连续，最新一行余额 == 当前可用积分；
  - **P4 风控冻结单据**：在审单（pending/appealed）与业务记录状态一致、冻结积分=业务成本、预占库存=奖品/商品账面 frozen；
  - **P5 库存账实**：应有 remain = 初始库存 − 有效消耗（revoked 不计）+ 库存调整凭证，逐 SKU（奖品按活动维度、商品按 goodsId）比对。
  - **P6 卡券账户**：有效券业务记录（normal/released 带 couponId）必须有券实例（漏发可补）；券实例必须回指一条有效业务记录（孤立券人工核查）；券码全局唯一（重复码人工核查）；已核销券必有核销人/时间；已过到期时刻仍 available 的券可自动补做到期。券库存（券奖品/券商品）仍由 P5 统一账实勾稽，发券/核销/补券不重复扣库存。
- **可追溯差异单**：一业务日一张单，保存首次快照、差异指纹签名、每次执行人/时间/结果、复核人与备注、全部补偿凭证；重复执行签名不变即同一版本，只追加执行痕迹。
- **复核后补偿（只追加，不改原始记录）**
  - 任务缺笔：按台账逐笔补记 `task-comp` 补偿流水并同步余额，按台账 id 幂等；若原始发奖流水仍存在则不补；
  - 积分净额少记（残差>0）：补记 `recon-comp` 流水；长款/多记（残差<0）不自动扣减，标记人工核查；
  - 库存盘亏/盘盈：不凭空回补或扣减实物，登记 -diff 的库存调整凭证把账面核销/补登到实物，保留调整前后快照；
  - 卡券漏发：按有效业务记录补发**新券**（新券码、有效期自补券日起算、券带「对账补券」标记并回指原业务记录），按 recordId 幂等不重复发；到期未流转补做 expired；孤立券/重复码/核销信息缺失只标记人工核查，不自动作废或改码；
  - 冻结单据不一致：引导至「风控申诉」处理，不自动核销预占。
- **跨日审核/补偿**：流水带 `bizDate`（归属业务日）与 `date`（实际处理日），任务/奖品跨日放行计入原业务日对账、不串当日账；补偿流水续在余额链末端保证快照链连续。历史流水完整留存，不按演示条数裁剪，避免历史净额、余额快照与领奖台账失去勾稽。
- **权限与同步**：仅运营可复核/补偿（用户视角只读）；补偿后余额、奖品/商品库存、运营看板、Tab 角标即时同步，补偿流水在积分中心带「对账补记/对账补偿」标记与归属日。
- 演示注入：对账页运营视角可注入「任务奖励漏记 +30」「商品盘亏 1 件」「卡券漏发 1 张」；种子另在上一业务日预置一笔 5 积分历史漏记，可完整走 对账 → 复核 → 补偿 → 再对账平账 闭环。
- 逻辑冒烟测试：`npm run test:recon`（覆盖六类口径检出、权限拦截、跨日补偿归属、流水留存、幂等防重、余额链自愈、库存核销、卡券 P6 检出/补发、看板同步、原始记录保留）。

## 实物收货发货说明

- **适用范围**：奖品与商品带 `physical` 标记（积分奖品/券卡/优惠券为虚拟，直接到账；其余实物走物流）。实物在中奖或兑换**成功后**才生成发货单。
- **状态机**：`待填地址 pending_address → 待发货 to_ship → 已发货 shipped → 已收货 received`
  - 用户中奖/兑换实物：自动生成「待填地址」发货单，在「📦 物流发货」填写收货人、手机号（11 位校验）、所在地区、详细地址；发货前允许修改；
  - 运营接单发货：「待发货」队列中查看收件信息，录入快递公司与快递单号（可选备注）后发货，物流信息对用户可见；
  - 用户确认收货：已发货订单一键确认收货，订单闭环。
- **风控联动**：命中风控的实物单**冻结期间不产生发货单**（库存仅预占、奖品未发放）；运营放行后才补发发货单；撤销则业务作废、库存/积分返还，始终无发货单。
- **权限与幂等**：用户只能填写/修改本人地址、确认本人订单；仅运营可接单发货；状态机保证不可跨状态操作、不可重复发货/重复收货；生成、填地址、发货、收货全部写入操作记录。
- **演示数据**：预置一笔已发货待确认的「500元购物卡」与一笔待填地址的「定制帆布袋」兑换；Tab 角标按视角提示（用户：待填地址+待收货；运营：待发货）。
- 逻辑冒烟测试：`npm run test:ship`（覆盖状态推进/表单校验/权限隔离/幂等防重/风控冻结-撤销-放行联动/审计留痕/对账仍平衡）。

## 卡券账户与核销说明

- **券类范围**：奖品与商品带 `couponId`（券模板定义在 `src/mock/data.js` 的 `COUPONS`）即为券类——满减券（门槛+减免）/ 代金券（面值）/ 兑换券（权益文案）。券类走卡券核销，与实物物流互斥；积分奖品等其余虚拟权益仍直接到账。券库存挂在奖品/商品的 stock/remain/frozen 上，与实物共用 P5 库存勾稽。
- **发券与风控联动（三态）**
  - 中奖/兑换正常落账：自动发券至用户卡券账户，生成全局唯一券码（`CP-XXXXX-XXXXX`），有效期自发券日起 `validityDays` 天（到期日 23:59 前可核销）；
  - 风控冻结：券库存 `remain-1 / frozen+1` **预占**，但**不生成券实例**（券码未发放），用户卡券页可见「预占待交付」提示；
  - 运营**放行**：核销预占库存并**交付发券**（有效期自**放行日**重新起算，写 `deliver` 台账）；运营**撤销**：库存回补、预占**释放**，券始终不存在（写 `revoke` 台账）。
- **用户出示 / 运营核销**
  - 用户在「🎟️ 卡券核销」查看卡券（待核销/已核销/已过期筛选）、复制券码到店出示；
  - 运营在扫码/输码工作台输入券码核销：券码自动归一化（忽略空格/连字符/大小写）；不存在、已核销（返回原核销人时间）、已过期三类均拦截；核销记录核销人、时间、渠道与备注，状态机幂等防重复核销。
- **到期处理**：每个业务动作（`syncBusinessDay` 入口）与运营核销前先执行卡券到期扫描，已过到期时刻的待核销券批量流转为 `expired`（幂等，只处理仍可用券）；核销入口对漏网的到期券做二次拦截并补做到期。
- **对账 P6 与补券**：卡券账户按「有效券业务记录 ↔ 券实例」逐笔勾稽，并校验券码唯一、核销信息完整、到期状态一致。漏发可在运营复核后补发**新券**（新券码、有效期自补券日起算、带对账补券标记，append-only 不伪造历史），按业务记录幂等；孤立券/重复码等只标记人工核查，不自动作废。演示可在对账页注入「卡券漏发 1 张」走完整闭环。
- **同步与留痕**：券发放/预占/交付/核销/到期/补券同步更新卡券账户、券库存（P5）、业务记录与运营看板/角标，并写 append-only 卡券台账与全局操作记录；原始券实例与台账不裁剪、不改写。
- **演示数据**：预置今日一张待核销满减券（`CP-A1B2C-3D4E5`）、今日与 10 天前各一张已核销券、13 天前一张已过期券，以及一张风控已申诉、预占待交付的「视频月卡」。
- 逻辑冒烟测试：`npm run test:coupon`（覆盖正常发券/券码唯一/有效期、运营核销权限与重复/过期/不存在拦截、风控预占-放行交付-撤销释放、抽奖中券、到期扫描幂等、P6 检出/补发/再对账平账、库存与看板同步、台账留痕）。

## 风控申诉说明

- **可配置规则**（「🛡️ 风控申诉」运营视角配置，即时生效）：高价值奖品稀有度、当日抽奖频次、短时连抽/连兑窗口、高价值兑换积分阈值、用户黑名单、风控总开关
- **审核单状态机**：`待审核 pending → 已申诉 appealed → 已放行 released / 已撤销 revoked`，仅待处理态可申诉/审核，重复提交自动拦截
- **冻结语义**
  - 积分：抽奖/兑换成本即时从可用余额转入冻结；放行则核销为消费（积分奖品此时才入账），撤销则原路返还
  - 库存：奖品/商品 `remain -1` 同时 `frozen +1` 预占（不超卖）；放行核销预占，撤销回补
  - 限次：冻结抽奖占用每日/累计次数，撤销后返还
  - 卡券：券奖品/券商品冻结期仅预占库存、不发券；放行后发券交付（有效期自放行日起算），撤销释放预占、券始终不发出
- **权限**：用户仅能对本人单据申诉；仅运营可放行/撤销/配置规则（页内可切换演示视角）
- **审计**：冻结、申诉、放行、撤销、规则变更、视角切换全部写入操作记录；积分流水 append-only，业务记录与看板统计随审核结果同步
